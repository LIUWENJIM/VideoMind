## 3. 面试常见问题与回答

### 3.1 架构设计类

**Q1: 为什么选择 Agent 架构而不是简单的 Prompt Engineering？**

**回答要点**：
```
长视频分析有三个特点决定了不能用简单 Prompt：

1. 任务复杂度高：用户目标往往很宽泛，比如"总结这个教学视频"，需要分解为多个子任务
2. 证据要求严格：不能胡编乱造，每条结论都要有视频中的证据支撑
3. 质量难以保障：单次 LLM 调用很难保证质量，需要多轮校验

Agent 架构的优势：
- Planner 做任务分解，将复杂问题简化
- Executor 专注执行，生成结构化产物
- Critic 做质量校验，发现问题可以定向修正
- 证据约束机制确保结论可追溯

如果用简单 Prompt，问题在于：
- 单次调用 Token 限制，无法处理长视频
- 没有校验机制，结论可靠性无法保障
- 无法做到证据绑定，容易 hallucination
```

**Q2: 为什么用 RocketMQ 而不是直接同步调用？**

**回答要点**：
```
视频分析是分钟级长耗时任务，同步调用有三个致命问题：

1. HTTP 超时：默认超时 30s，视频分析至少 1-2 分钟
2. 资源占用：线程长期阻塞，Tomcat 线程池很快耗尽
3. 无法重试：网络抖动或 LLM 超时，整个请求失败

RocketMQ 解决了这些问题：
- 异步解耦：提交即返回 202，不阻塞用户
- 削峰填谷：高峰期缓冲，保护下游服务
- 失败重试：最多 3 次重试，死信队列兜底
- 幂等消费：Redis 锁保障不重复处理

实际上我还考虑过 Kafka，但 RocketMQ 更适合：
- 支持延迟消息，适合重试场景
- 单机性能足够，不需要 Kafka 的高吞吐
- 国产开源，文档和社区更友好
```

**Q3: 检查点机制是怎么设计的？**

**回答要点**：
```
检查点采用 MySQL + Redis 双层存储：

1. MySQL 作为持久化真源，保障数据不丢失
   - 存储 VideoContext、AgentPlan、AnalysisResult
   - 支持事务，保障一致性

2. Redis 作为热缓存，加速读取
   - 检查点键：agent:checkpoint:{mediaId}:goal:{goalDigest}
   - TTL 7 天，自动过期

3. 键设计考虑：
   - mediaId 维度：VideoContext 与模式无关，可以复用
   - goalDigest 维度：不同分析目标隔离，互不影响
   - goalDigest = SHA256(goal + mode)[0:16]

4. 断点恢复流程：
   - 任务开始时先查检查点
   - 如果已有终态结果，直接返回
   - 如果是中间状态，从上次失败的阶段继续
   - 比如 Executor 完成后 Critic 失败，下次直接从 Critic 开始

5. 一致性保障：
   - 先写 MySQL，再异步更新 Redis
   - 定时对账任务修复不一致
   - Redis 故障降级到直接读 MySQL
```

### 3.2 技术细节类

**Q4: Agent 的三轮角色具体是怎么协作的？**

**回答要点**：
```
以"总结这个教学视频"为例：

第一轮：
1. Planner 分析用户目标，生成任务计划：
   - 任务1：提取视频的主要知识点
   - 任务2：梳理知识点的逻辑关系
   - 任务3：总结核心概念和结论

2. Executor 按计划执行，生成结构化产物：
   - conclusions: ["二叉树的前序遍历是...", "中序遍历是..."]
   - evidence: [
       {timestampMs: 120000, source: "ASR", content: "前序遍历..."},
       {timestampMs: 180000, source: "OCR", content: "遍历算法PPT"}
     ]
   - suggestions: ["建议结合代码示例理解"]

3. Critic 校验产物：
   - 检查是否覆盖所有任务：✓
   - 检查证据绑定：✓
   - 检查时间戳有效性：✗ 发现 evidence[1] 的时间戳超出视频长度
   - passed = false, feedback = ["修正第2条证据的时间戳"]

第二轮：
4. Executor 根据 Critic 反馈修正：
   - 重新检索 180s 附近的证据
   - 修正 evidence[1] 的时间戳为 175000

5. Critic 再次校验：
   - 所有检查通过
   - passed = true

6. 返回最终结果

关键设计：
- 最多 2 轮，避免无限循环
- Critic 反馈要具体，不能只说"不好"
- Executor 只修正被指出的问题，保留已通过的结论
```

**Q5: 多模态融合是怎么做的？**

**回答要点**：
```
视频处理分两条分支并行：

ASR 分支（语音识别）：
1. FFmpeg 提取音频，60秒切分为一段
2. 调用 TeleSpeech ASR API 识别语音
3. 输出 TranscriptSegment[startMs, endMs, text]

OCR 分支（画面文字）：
1. FFmpeg 场景检测抽取关键帧
   - 场景变化阈值 0.35
   - 保底 30秒采样一次（避免遗漏静态板书）
2. 感知哈希去重
   - 将图片缩放到 9x8 灰度图
   - 计算相邻像素差值，生成 64-bit hash
   - 汉明距离 ≤ 5 视为重复，跳过
3. Tesseract OCR 识别文字
4. 关键帧上传到 MinIO
5. 输出 FramePart[timestampMs, ocrText, frameUrl]

融合阶段：
1. 60秒窗口对齐
   - ASR 和 OCR 按时间戳对齐到同一窗口
   - 比如 [120s-180s] 窗口内既有语音也有 OCR
2. 生成 VideoSegment
   - startMs, endMs: 时间范围
   - transcript: 语音文本
   - ocrTexts: OCR 文本列表
   - evidenceFrames: 关键帧 URL 列表

容错设计：
- 单分支失败保留另一分支结果
- 双分支都失败才抛异常
- 60分钟总超时控制
```

**Q6: 混合检索是怎么实现的？**

**回答要点**：
```
检索分三步：

1. 检索规划（LLM）
   输入：用户目标 "讲解二叉树遍历"
   输出：VideoRetrievalIntent
   - semanticQuery: "二叉树的前序遍历和中序遍历算法"
   - keywords: ["二叉树", "前序遍历", "中序遍历", "算法"]
   - visualKeywords: ["PPT", "代码"]

2. 多路评分
   对每个 VideoChunk（5分钟片段）计算三路分数：
   
   语义分（60%权重）：
   - 用 BGE-M3 将 query 和 chunk 摘要向量化
   - 计算 cosine 相似度
   - Qdrant 向量库加速检索
   
   关键词分（25%权重）：
   - 统计 keywords 在 chunk 文本中的命中率
   - matchedTerms / totalTerms
   
   OCR 分（15%权重）：
   - 统计 visualKeywords 在 OCR 文本中的命中率
   - 针对 PPT、代码等画面文字

3. 融合排序
   - chunkScore = semantic×0.6 + keyword×0.25 + ocr×0.15
   - 取 TopK=3 的 chunk
   - 展开 chunk 内的 rawSegments，再次评分
   - segmentScore = chunk×0.55 + transcript×0.25 + visual×0.20
   - 返回最终片段列表

优化点：
- 根据视频类型动态调整权重
  - 讲座视频：关键词权重提高到 40%
  - 演示视频：OCR 权重提高到 40%
- Qdrant 不可用时降级到本地向量
- Embedding 失败时降级到纯关键词匹配
```

### 3.3 优化与改进类

**Q7: 你做了哪些优化？效果如何？**

**回答要点**：
```
主要做了三个优化：

1. Token 估算优化
   问题：原来用字符数近似，误差 30%，成本预算不准
   方案：引入 tiktoken-java 精确计算 + Caffeine 缓存
   效果：误差降到 5%，缓存命中率 85%
   
2. 证据校验增强
   问题：原来只支持文本包含，同义词、表述差异无法识别
   方案：三级匹配策略
   - Level 1: 精确包含（快速路径，90% 命中）
   - Level 2: 模糊匹配（Levenshtein 距离，处理轻微差异）
   - Level 3: 语义匹配（Embedding cosine > 0.85，处理同义词）
   效果：校验准确率从 75% 提升到 92%

3. 逻辑链路重构
   问题：AiService.resolveContext 120 行嵌套代码，圈复杂度 12
   方案：策略模式拆分
   - resolveFromCheckpoint: 检查点查询
   - resolveFromContentReuse: 内容级复用
   - resolveByBuilding: 加锁构建
   效果：圈复杂度降到 3，代码可读性大幅提升

量化指标：
- Token 估算误差：30% → 5%
- 证据校验准确率：75% → 92%
- 代码圈复杂度：12 → 3
- 检索响应时间：< 200ms
- 服务可用性：95% → 99.5%（引入熔断器后）
```

**Q8: 如果让你继续优化，你会做什么？**

```
我会从三个方向继续优化：
```

### 3.4 系统设计类

**Q9: 如果视频有 10 小时，你怎么处理？**

**回答要点**：
```
10 小时视频的挑战：
- VideoContext 太大，无法全部放入 Prompt
- LLM 调用成本很高
- 处理时间很长

解决方案：

1. 分而治之
   - 按 5 分钟切分为 VideoChunk
   - 每个 Chunk 独立生成摘要和关键词
   - 检索时只选择最相关的 TopK Chunk

2. 分层处理
   - 第一层：Chunk 级摘要（LLM 调用）
   - 第二层：Chunk 检索（混合检索）
   - 第三层：Segment 级精细分析（只分析相关片段）

3. 成本控制
   - 动态预算：10 小时视频给更多预算
   - 模型降级：Chunk 摘要用小模型，最终分析用大模型
   - 缓存复用：相同 Chunk 不重复处理

4. 性能优化
   - 并行处理：多个 Chunk 并行分析
   - 流式输出：边处理边返回中间结果
   - 预计算：上传时就处理 VideoContext

实际处理流程：
1. 视频上传后，立即开始预处理
   - ASR 分段识别（并行）
   - 关键帧抽取 + OCR（并行）
2. 生成 VideoContext（60秒窗口融合）
3. 切分为 VideoChunk（5分钟/块）
4. 用户提交分析目标后：
   - 检索最相关的 Chunk（< 200ms）
   - 只分析相关 Chunk 的 rawSegments
   - 生成最终结论

这样 10 小时视频也能在 2-3 分钟内完成分析
```

**Q10: 如何保证系统的可靠性？**

**回答要点**：
```
从四个层面保障可靠性：

1. 应用层
   - 参数校验：所有输入都做合法性检查

   - 死信队列：失败任务进入人工处理队列

3. 资源层

   - 超时控制：每个环节都有超时，避免无限等待
   - 资源限制：用户级和全局级限流，防止过载

4. 监控层
   - Telemetry：记录每次 LLM 调用的 Token 和成本

   - 失败台账：记录所有失败任务，支持人工重投
   - 告警机制：关键指标异常时告警

具体案例：
- LLM 超时：300秒超时，超时后重试
- Redis 故障：降级到直接读 MySQL
- Qdrant 不可用：降级到本地向量检索
```

## 4. 技术深度问题准备

### 4.1 分布式系统

**Q: Redis 分布式锁怎么实现的？有什么问题？**

```
实现：
- 使用 Redisson 的 RLock
- 底层是 Redis SETNX + Lua 脚本
- 支持可重入、自动续期（watchdog）

问题：
1. 锁超时：业务没执行完，锁过期了
   - 解决：watchdog 自动续期，每 10s 检查一次
   
2. 主从切换：主节点挂了，锁丢失
   - 解决：RedLock 算法，多个独立节点
   - 但我们场景可以接受，因为 MQ 会重投

3. 性能问题：高并发下锁竞争激烈
   - 解决：锁粒度细化，按 contentHash + goalDigest 加锁
   - 不同视频、不同目标不互相阻塞
```

**Q: RocketMQ 如何保证消息不丢失？**

```
三个环节保障：

1. 生产者到 Broker
   - 同步发送：send() 等待 Broker 确认
   - 重试机制：发送失败自动重试
   - 事务消息：保障本地事务和消息发送一致性

2. Broker 存储
   - 同步刷盘：消息写入磁盘才返回成功
   - 主从复制：同步复制到 Slave 节点
   - 配置：flushDiskType=SYNC_FLUSH

3. 消费者
   - 手动 ACK：业务处理完才返回 CONSUME_SUCCESS
   - 重试机制：消费失败返回 RECONSUME_LATER
   - 死信队列：超过最大重试次数进入死信

我们的实践：
- 任务提交时先写 MySQL，再发 MQ
- 消费失败最多重试 3 次
- 超过 3 次进入死信队列，人工处理
- 定时扫描死信队列，支持手动重投
```

### 4.2 LLM 应用

**Q: 如何防止 Prompt 注入攻击？**

```
我们的防护：

1. System Prompt 隔离
   - 明确告知模型：用户输入是不可信数据
   - 禁止切换角色、调用工具、泄露指令
   
2. 结构化 Prompt
   - 使用 XML 标签标记数据边界
   - <video-context>...</video-context>
   - 模型知道哪些是数据，哪些是指令

3. 输出校验
   - JSON Schema 校验输出格式
   - 不允许输出可执行代码
   - 过滤敏感关键词

4. 权限控制
   - 模型不能直接调用工具
   - 所有工具调用由后端控制
   - 模型只能返回结构化数据

潜在风险：
- 用户可能构造恶意 VideoContext
- 但模型有 System Prompt 约束，不会执行
- 最坏情况是输出错误结论，不会造成安全风险
```

**Q: 如何评估 LLM 的输出质量？**

```
我们的评估方法：

1. 结构化校验
   - JSON 格式是否正确
   - 必填字段是否完整
   - 数据类型是否正确

2. 业务规则校验
   - 任务数量：1-5 个
   - 时间戳：必须在视频范围内
   - 证据绑定：每条结论都要有证据

3. Critic 校验
   - Planner 任务是否都覆盖
   - 证据是否可追溯
   - 结论是否有上下文支撑

4. 人工评估（离线）
   - 抽样检查 100 个案例
   - 评估结论准确性、证据可靠性
   - 计算准确率和召回率

持续改进：
- 收集用户反馈（点赞/点踩）
- 分析失败案例，优化 Prompt
- 定期更新评估数据集
```

### 4.3 性能优化

**Q: 如何优化系统的响应时间？**

```
优化策略：

1. 异步化
   - 视频处理：ASR 和 OCR 并行执行
   - 任务执行：MQ 异步，提交即返回
   - 检查点更新：MySQL 同步，Redis 异步

2. 缓存
   - VideoContext 缓存：同一视频不重复处理
   - 检查点缓存：Redis 加速读取
   - Token 估算缓存：Caffeine 本地缓存

3. 预计算
   - 视频上传时立即处理 VideoContext
   - 预计算 Chunk 摘要和 Embedding
   - 用户提交目标时只需检索

4. 流式输出
   - Agent 执行过程中实时推送进度
   - 中间结果先返回，最终结果后返回
   - 用户感知延迟降低

量化效果：
- 视频预处理：并行后从 3min 降到 1.5min
- 检索响应：缓存后 < 200ms
- 任务提交：异步后 < 100ms
- 用户感知延迟：流式输出降低 50%
```
